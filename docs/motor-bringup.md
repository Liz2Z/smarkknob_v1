# 2804 电机调试记录与当前配置

记录日期：2026-10-18（Asia/Shanghai）。

后续已增加 **Wi-Fi HTTP 动态调参及本机管理后台**，见 [HTTP/API 使用说明](http-api.md)。
下文保留此前调试历史；当前幅值和频率可通过接口直接设置，不再需要每次编译。
HTTP 配置范围为 0.5–2V、0–100Hz，支持 forward/reverse 方向设置，默认仍为 1V/8Hz；参数修改不自动启动。

## 当前结论

- 已实现三相正弦 PWM 开环转动和 AS5600 独立任务角度采集；尚未实现使用角度反馈的闭环 FOC 或智能旋钮力反馈。
- 固件默认持续参数为 **12V 母线、1V 电压幅值指令、8Hz 电角频率**。用户曾确认“更快且平稳”；现可通过 HTTP 动态修改。
- **切换到 HTTP 服务前最后一次操作为停机**：串口持续控制进程正常退出，随后补发停止命令，收到 `STOPPED`。当前运行状态以管理后台或 `/api/status` 为准。
- 1V 可作为后续调试基准，但不是已经认证的长期安全参数；绕组电流、温度、带载能力都还没有实测。
- 此前 2V/0.5Hz 持续运行出现明显发烫，约 169 秒时捕获故障低电平。不能恢复该配置并直接长期运行。

| EN=0 的 PWM 自检 | `edges=801/801/800 nFTlow=0`，采样窗口 20ms | C3 三个 GPIO 有 PWM；不能证明驱动功率输出正常，也不能排除漏采的短脉冲 |
| 8V 指令、0.5Hz、最多 1 秒，电机接入 | 两次启动均返回 `FAULT LOW STOPPED`；用户反馈有动作或声音 | 未持续运行到预定结束时间，不能视为稳定旋转成功 |
| 拔掉 M1/M2/M3 电机线，进行相同空载测试 | 脚本运行到自动停机，退出码 0，停机后故障脚为 HIGH | 该次无电机负载测试未报故障，不能据此认定驱动板所有功能正常 |
| 启动前故障脚持续 LOW | 被动上拉、下拉均读到 0；用户随后发现电源线断开 | 供电中断是一次明确发现的问题，不能追认全部早期失败都由它造成 |
| 重新接好电源 | 启动前故障脚恢复 HIGH | 具备继续短时启动测试的条件，但 HIGH 不保证运行时不出故障 |
| 12V 指令、0.5Hz | `FAULT LOW STOPPED t=110596us`；用户报告“动了” | 约 0.11 秒就停机，仍在 0.2 秒固定磁场对齐阶段，尚未进入持续旋转阶段 |
| 2V 幅值、0.5Hz 持续模式 | 用户确认持续慢转；后报告“很烫”；日志为 `FAULT LOW STOPPED t=169005243us` | 能转不代表持续温升合适；具体故障类型未确定 |
| 1V 幅值、1Hz，3 秒 | 正常停止，无故障；用户确认更快且平稳 | 短时转动验证通过，不能证明长期温升合适 |
| 1V 幅值、2Hz，30 秒 | 正常停止，无故障；用户报告没有明显升温 | 通过一次 30 秒观察，未测温，也未验证热稳态 |
| 1V 幅值、4Hz 持续模式 | 用户确认更快且平稳、没有明显升温；随后按要求停机 | 可作为已试过的低幅值配置，持续时长和温度未量化 |
| 1V 幅值、8Hz 持续模式 | 用户确认更快且平稳；随后按要求停机并收到 `STOPPED` | 当前速度配置可带动电机；该档长期温升未单独验证 |

### 为什么高电压指令没持续转，低电压指令反而能转

本次至少涉及供电连接、故障停机、运行时长与驱动模式几个因素，不能只比较电压数字。

高幅值测试因故障提前停机，12V 指令那次甚至没有完成启动对齐。
低幅值持续模式则能继续改变磁场方向，让转子跟随。
这说明不需要靠不断增大幅值才能使它旋转，但不能据此确定高幅值故障一定是过流或欠压。

### 为什么 2V 能转却严重发热

2V 是电压指令，不是电流限制。当前控制没有根据负载闭环调节电流。
低速时反电动势较小，如果绕组电阻低，即使低电压也可能产生较大电流。
绕组铜耗与电流平方有关，长时间通电会积累热量；固定幅值也可能超过维持空载转动实际需要的驱动力。

高幅值那次仅运行约 0.11 秒，2V 持续模式则运行约 169 秒，不能把两者温升直接比较。
尚未测量电流、绕组电阻和温度，所以这里只能解释可能机制，不能给出确定的过热根因。
之前只验证了“能转、短时不报错”，没有验证持续温升，就让它长期运行，这一步依据不足。

## 电源电压、幅值、频率的区别

- **电源电压**：驱动板的外部母线，本次一直按 12V 配置。
- **电压幅值**：程序生成的三相电压目标相对中间参考值的峰值。例如 1V 幅值对应目标波形在参考点上下各变化 1V。
- **PWM 载波频率**：20kHz，用于开关驱动，不是电机每秒转 20000 次。
- **电角频率**：当前持续模式为 8Hz，决定旋转磁场的速度。机械转速还取决于极对数及转子是否同步跟随。

同步跟随时，理论机械转速为 `rpm = 60 × 电角频率 / 极对数`。
本次没有编码器测速，不能把该理论值当成实际测得的转速。

当前 1V/8Hz 持续模式不削顶。
另一个保留的 f/r 脉冲诊断模式仍使用 **12V 指令、0.5Hz、最多 1 秒**：
12V 母线下，居中正弦调制的线性幅值上限为 6V，超过后 PWM 会削顶。
代码将比较值钳位在 0..2047；“12V 指令”不能称为实测或完整的 12V 相电压。
**不要误用 `forward` / `reverse` 来复现已经验证的 1V 持续配置。**

## 当前软件与保护机制

| 文件 | 职责 |
|---|---|
| `src/bin/motor_driver.rs` | ESP32-C3 GPIO、LEDC 三相 PWM、USB 命令、故障输入及停机 |
| `motor-control/src/lib.rs` | 波形、启动对齐、限时脉冲、持续模式保活与更新间隔检查 |
| `scripts/motor.py` | 串口控制、持续保活、退出补发停止 |
| `scripts/test_motor.py` | 主机启动握手和保活行为测试 |

持续模式参数在 `motor-control/src/lib.rs`：

| 参数 | 当前值 |
|---|---|
| `SUPPLY_VOLTS` | 12.0V |
| `CONTINUOUS_VOLTS` | 1.0V |
| `CONTINUOUS_PERIOD_US` | 125000µs，即 8Hz |
| `ALIGN_US` / `RAMP_US` | 200000µs，即启动前 0.2 秒固定方向并渐增幅值 |
| `KEEPALIVE_US` | 500000µs，即 0.5 秒保活租期 |
| `MAX_UPDATE_GAP_US` | 20000µs，即最大 20ms 更新间隔 |
| PWM | 20kHz、11bit；正常更新周期约 500µs |

已实现的保护：

- 上电不自动转动；先 `arm`，10 秒内发送启动命令。
- 故障脚 LOW 时拒绝启动；运行中捕获 LOW 则关闭 EN，再发送故障回包。
- 持续模式缺少主机保活时停机；迟到的保活不能复活已停止的运行。
- 更新停顿超过 20ms、未知命令、命令溢出、Ctrl-C/Esc 或 panic 都关闭输出。
- USB 回包为非阻塞，避免日志等待阻塞停机。
- 脉冲运行不能靠重复命令延长截止时间。

这些保护不包含绕组电流闭环、绕组温度检测或自动温度降额。
DRV8313 的芯片故障保护不能当作电机绕组的温控保护。

## 操作与复现

以下命令在项目根目录执行，串口默认 `/dev/cu.usbmodem21201`。

```sh
# 构建和烧录；不会自动启动电机
cargo build --offline --locked --release --bin motor-driver
espflash flash --port /dev/cu.usbmodem21201 --non-interactive --skip-update-check target/riscv32imc-unknown-none-elf/release/motor-driver

# 启动前检查；诊断不会使能电机
python3 scripts/motor.py fault
python3 scripts/motor.py diag

# 当前 1V/8Hz 参数的短时试运行
python3 scripts/motor.py continuous --seconds 3

# 持续运行：应在已确认冷却、接线和温升观察条件后手动执行
python3 scripts/motor.py continuous
```

持续运行时，在占用串口的同一终端按 **Ctrl-C**，脚本会补发停止命令并退出。
释放串口后可再确认：

```sh
python3 scripts/motor.py stop
```

不要在持续进程运行时用另一个程序打开同一串口，以免干扰连接或复位主控。
若明显发热、卡顿或出现异味，断开驱动板 12V 并冷却，不依赖故障脚替代温度判断。
启动前 nFT 为 LOW 时，先检查供电、连接及故障状态，不屏蔽保护强行启动。

停机状态回包中的 `cmd=12V clipped 0.5Hz` 描述的是保留的 f/r 脉冲配置，
不是当前正在运行 12V，也不是持续模式的配置。持续模式启动回包应为：

```text
RUN continuous 1V 8Hz; keepalive 500ms
```

python3 -m unittest discover -s scripts -p 'test_*.py'
cd /tmp

## 反馈与限流：后续方案，尚未实施

### AS5600 角度反馈

可先保留现有驱动板，接 AS5600 实现带角度反馈的电压模式 FOC，不必因为没有电流采样就立即换板。
当前已按以下引脚实现 I²C 并读到 AS5600；此前建议接线现已通过通信验证：

| AS5600 | ESP32-C3 |
|---|---|
| VCC | 3V3，前提是具体模块支持 3.3V，I²C 上拉也接 3.3V |
| GND | GND |
| SDA | GPIO20，软件显式配置 |
| SCL | GPIO21，软件显式配置 |

还需安装合适的磁铁、校验角度连续性和磁场状态，确认极对数、方向及电角度零点，再实现 FOC。
角度反馈可用于控制磁场方向，但本身不提供实际电流限幅，也不能保证不会过热。

### 电流与温度反馈

- 真正的相电流闭环需要增加电流采样硬件，或换带采样的三相驱动板；仅把软件变量命名为“电流限制”不等于实测限流。
- 保留现板的一种方案是两相串联采样电阻，配双向、适合 PWM 相线的采样放大器，例如 INA240，再接 MCU ADC。量程、偏置、布线及校准需要单独设计。
- 可限流电源有助于限制和观察整体输入功率，但电源输入电流不等于每相绕组电流，不能替代相电流闭环。
- 应测量绕组参数、运行电流和温升，增加温度检测或停机阈值；不能直接把未经确认的“180mA”当作相电流安全上限。

## 尚未确认

- 电机准确型号、7.2V 与 12V 参数的关系、极对数、绕组电阻及电感。
- 8V/12V 指令触发 nFT 的具体原因：过流、供电掉压、过热或干扰尚未区分。
- 1V/8Hz 下实际机械转速、绕组电流、长时间及带载温升。
- 静止保持、模拟段落和力反馈等智能旋钮工作模式的电流与温升。
- AS5600、闭环 FOC、实际电流限流与电机温度保护都尚未实现。

## 2026-10-18：ESP32-C3 主芯片发热对照

用户报告所有外接线拔掉、仅 USB 供电时，主芯片仍持续发烫；没有实测温度、电流，尚不能确定硬件是否损坏。
原电机固件最高 CPU 频率、主循环忙轮询，Wi-Fi 省电关闭，可能贡献功耗。
已增加并烧录 `idle-diagnostic`：80MHz、未初始化无线、无网络/PWM/传感器轮询，GPIO4/5/6/7 置低，主循环 WFI 等待中断。
它是空闲功耗对照程序，不是温度测量或深睡眠程序。运行期间 HTTP 后台离线，不能控制电机。
构建与 clippy 通过，espflash 返回烧录成功；实际降温效果尚待用户观察。

```sh
cargo build --offline --locked --release --no-default-features --bin idle-diagnostic
espflash flash --port /dev/cu.usbmodem21201 --non-interactive --skip-update-check target/riscv32imc-unknown-none-elf/release/idle-diagnostic
```

先断电冷却，保持外接线断开，再仅 USB 短时观察；如果仍快速明显发烫，断电并排查板子/USB 供电，不据此断言必定损坏。恢复电机与网络服务需要重新烧录 `motor-driver`，不会自动恢复。


### 诊断结果与恢复功耗优化版

用户反馈 `idle-diagnostic` 下“不烫了”。随后按用户“优化”要求恢复 `motor-driver`，改为 CPU 80MHz、停机任务定时等待 5ms、运行等待 500µs 控制时点，Wi-Fi 停机 Minimum 省电/运行 None。

### AS5600 停机诊断读取与实时页

用户确认编码器接线已完成，但未安装到电机。已加入只读驱动：I²C 地址 0x36、GPIO20/SDA、GPIO21/SCL、100kHz，分别读取 STATUS(0x0B) 与 RAW_ANGLE(0x0C/0x0D)。每个 I²C 事务配置 2ms 软件超时，不进行配置寄存器或 OTP 写入。
停机时每 100ms 尝试采样；运行时不进行阻塞 I²C，避免占用电机控制周期，因此当前不是可用于实时换相的闭环编码器实现。
本机后台新增“磁编码器”导航页，约每 200ms 请求最新缓存状态，展示连接、磁场状态、原始寄存器、角度与采样年龄。页面隐藏时暂停状态轮询。

已烧录并读到 `online:true`、`status:19 (0x13)`、`magnet:missing`，说明 I²C 通信成功，但该时刻未检测到磁铁。无磁场时原始寄存器可能跳动，不能视为真实角度；API 返回 `angle_valid:false` 和 `angle_deg:null`。初版页面显示“—”；随后按用户反馈改为始终展示原始值换算角度，硬件磁场条件未满足时标注“未验证”，API 有效性语义不变。
用户需用配套径向磁铁对准芯片、手动旋转验证连续性，安装到电机后再做方向、极对数和零位校准。未自动启动电机或校准。

### 持续并行采集：替代停机诊断

用户指出运行时停采集无法进行反馈。当前已将 AS5600 采集从主控制循环移到独立 RTOS 任务：
- 电机/HTTP 主任务优先级 1，采集任务优先级 0；不持锁进行 I²C 或等待。
- Blocking I²C 外设安全移交任务后，在任务内转换为 Async，尊重 Async 外设的 !Send/核心绑定约束；采集任务固定在 CPU0。
- 总线 100kHz，从 STATUS(0x0B) 连读三字节获得状态和 RAW_ANGLE，减少调度往返；硬件总线超时 1000 个总线周期、软件事务超时 20ms。
- 正常传输由硬件进行，采集任务每次 Pending 让出 CPU 100µs；运行目标周期 5ms、停机 100ms。
- HAL 异常恢复可能消耗最多约 50ms，但发生在低优先级、可抢占的采集任务；失败后退避 1s，清除旧数据并累计错误。
- 主循环仍以 500µs 为控制目标，保留 20ms 更新停顿保护、500ms 保活、运行时长与故障保护。

这一步提供边运行边采集，没有启用角度反馈换相或 PID。编码器尚需机械固定、验证磁场、校准极对数/零位/方向，才能进一步实现闭环。未验证磁场的原始值不能自动作为闭环反馈。
